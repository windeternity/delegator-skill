Use it as a pattern for how to think about routing, and maintain real model facts in your own project-local roster.

This is a dated routing suggestion, not a hard rule or benchmark. Use it as a
model/task fit checklist after the project-local `AGENT_ROSTER.md` records what
the user actually has available.

If the user's model is not listed here, do not guess from the name. Use the
classification method in this file together with
`references/unknown-model-discovery.md`: research current reliable sources when
available, map the model to generic capabilities, record the evidence level in
the roster, and run a small smoke test before assigning serious work.

# Vibe Coding 模型任务分配清单

版本：v1.0  
用途：作为通用模型选型与任务分配文档，不依赖具体开发工具或平台。  
原则：本文不做排名、不打分，只描述不同模型更适合承担的任务类型、使用边界和风险。

---

## 1. 使用原则

### 1.1 不按“最强模型”单线选择

Vibe Coding 不是只比较模型智商，而是要看模型在不同任务中的适配度。一个模型可能适合快速实现，但不适合最终审计；另一个模型可能适合复杂复核，但不适合高频小修。

更合理的做法是按任务分配模型：

- 需求澄清与产品原型
- 日常功能开发
- 中大型工程推进
- 代码审计与风险复核
- 多模态 UI / 截图 / PDF / 视频理解
- 长上下文资料消化
- 高风险操作终审
- 快速摘要、日志分析、小修小补

### 1.2 不让轻量模型硬扛重任务

不同模型的参数量级、上下文长度、推理深度和稳定性差异很大。Flash、Plus、Preview、Lite 这类定位的模型可以用于快筛、初稿、小修、摘要和低风险执行，但不应该单独承担重型任务。

重型任务包括：

- 大规模重构
- 复杂 PR 审计
- 核心业务逻辑修改
- 高风险删除或回滚判断
- 多模块架构调整
- 长项目路线判断
- 需要强证据链的事实核验

### 1.3 模型参数不透明时要保守使用

如果模型没有明确公布参数量级，或者主要优势来自长上下文、多模态、工具链适配、产品包装，就不要默认把它当作最强推理模型。它仍然可以很适合执行、原型、多模态理解，但不应直接承担最终裁判任务。

### 1.4 最终判断和执行可以分离

一个稳定的 Vibe Coding 流程通常是：

1. 用适合执行的模型做第一轮实现。
2. 用适合审计的模型做复核。
3. 用最高可信模型做最终路线、合并、删除、核心逻辑判断。

## 2. 任务类型总览

### 2.1 产品原型 / UI / 多模态任务

适合模型：

- Gemini 3.1 Pro
- MiniMax M3
- Qwen3.7 Plus
- Kimi K2.6

适合场景：

- 根据截图分析页面问题
- 根据产品想法生成页面结构
- 根据 PDF / 图片 / 视频整理需求
- 视觉还原、前端交互、界面体验分析
- 从模糊需求推进到可运行原型

不建议优先使用：

- DeepSeek V4 Pro
- DeepSeek V4 Flash
- GLM-5.1
- Hy3 Preview

原因：这些模型更偏文本、代码、推理或轻量执行，不是最适合视觉理解和多模态产品任务。

### 2.2 日常功能开发

适合模型：

- Claude Sonnet 4.6
- GLM-5.1
- Qwen3.7 Max
- Qwen3.7 Plus
- MiniMax M3
- MiMo V2.5 Pro

适合场景：

- 加页面、组件、接口、配置项
- 修普通 bug
- 补测试
- 实现中小型功能
- 根据现有代码风格做局部扩展
- 对已有项目做小到中等规模改动

使用边界：

- 要给明确范围
- 要限制可修改文件
- 要指定测试命令
- 要禁止顺手重构
- 要要求失败时停止并报告

### 2.3 中大型工程推进

适合模型：

- Claude Opus 4.8
- Claude Opus 4.7
- Kimi K2.6
- MiMo V2.5 Pro
- Qwen3.7 Max
- DeepSeek V4 Pro

适合场景：

- 多模块功能推进
- 重构前规划
- 多阶段任务拆解
- 复杂 bug 修复
- 长项目连续迭代
- 多文件、多测试、多轮反馈任务

不建议单独使用：

- DeepSeek V4 Flash
- Qwen3.7 Plus
- Hy3 Preview

原因：这些模型可以参与初稿、快筛、局部修复，但不适合独立承担长程复杂工程任务。

### 2.4 代码审计 / PR 复核 / 风险判断

适合模型：

- DeepSeek V4 Pro
- Claude Opus 4.8
- Claude Opus 4.7
- GPT-5.5
- Kimi K2.6

适合场景：

- PR review
- 复杂 bug 根因分析
- 分支、commit、diff、文件状态核验
- 判断某个改动是否已经进入主线
- 判断改动是否越界
- 判断测试是否足够覆盖风险
- 发现“看起来通过但实际不安全”的问题

不建议单独使用：

- MiniMax M3
- DeepSeek V4 Flash
- Qwen3.7 Plus
- Hy3 Preview

原因：它们可以做第一轮审查或辅助发现问题，但高风险复核需要更强的证据链能力和稳定性。

### 2.5 高风险终审

适合模型：

- GPT-5.5
- Claude Opus 4.8
- DeepSeek V4 Pro

适合场景：

- 是否合并主分支
- 是否删除分支或目录
- 是否清理历史工作区
- 是否修改核心业务逻辑
- 是否推进项目阶段
- 是否接受某个模型的执行结果

不建议使用：

- Flash / Plus / Preview / Lite 定位模型
- 参数不透明且缺少稳定验证的模型
- 主要面向执行或原型的模型

## 3. 模型任务清单

## 3.1 GPT-5.5

定位：最终裁判、项目总控、高风险终审模型。

适合任务：

- 项目路线判断
- 是否进入下一阶段
- 高风险删除、合并、回滚前的终审
- 多模型意见冲突时做最终裁决
- 复杂 PR 的最终风险判断
- 核心业务逻辑是否越界
- 将执行模型的回报压缩成下一步任务

不适合任务：

- 高频低价值小修小补
- 简单日志摘要
- 大量重复性文档格式处理
- 单纯当最大上下文执行器使用

使用建议：

GPT-5.5 应放在“最终判断层”，不是所有任务都让它亲自执行。它适合判断方向、风险、边界和是否可以继续推进。

---

## 3.2 Claude Sonnet 4.6

定位：稳定主力开发模型。

适合任务：

- 日常功能开发
- 中等复杂 bug 修复
- 前后端常规任务
- 测试驱动开发
- 中小型 PR 实现
- 代码结构调整
- 需求明确的工程实现

不适合任务：

- 极高风险终审
- 特别复杂的长程重构裁判
- 删除、回滚、合并等不可逆操作的最终判断
- 需要最高推理深度的架构争议

使用建议：

Sonnet 4.6 适合作为常规开发主力。它比轻量模型稳，比重型模型更适合日常高频使用。复杂任务失败或卡住时，再升级给 Opus 4.7 / 4.8 或 GPT-5.5。

---

## 3.3 Claude Opus 4.7

定位：重型工程审阅与复杂开发模型。

适合任务：

- 复杂 PR review
- 大仓库理解
- 复杂 bug 根因分析
- 长程代码任务
- 多模块工程修复
- 技术债判断
- 高难度代码重构规划

不适合任务：

- 简单小修
- 普通文档整理
- 低风险格式化
- 大量重复性任务

使用建议：

Opus 4.7 适合作为重型工程模型。遇到 Sonnet 4.6 无法稳定解决的问题，可以交给 Opus 4.7 做深度审阅或复杂实现。

---

## 3.4 Claude Opus 4.8

定位：最高难度工程任务与深度判断模型。

适合任务：

- 长程复杂工程任务
- 多服务、多模块、多阶段开发
- 高风险技术方案审阅
- 架构级问题分析
- 复杂代码库探索
- 对关键实现方案提出反驳意见
- 困难 bug 的最终技术复核

不适合任务：

- 简单功能开发
- 小 bug 快修
- 低风险文档任务
- 不需要深度判断的批量执行

使用建议：

Opus 4.8 应作为“工程总监型模型”。它适合处理最难的问题，但不应浪费在普通小任务上。

---

## 3.5 Gemini 3.1 Pro

定位：多模态产品脑、UI 理解和长资料综合模型。

适合任务：

- 截图驱动的 UI 分析
- PDF、图片、视频理解
- 产品原型设计
- 前端视觉还原
- 复杂需求拆解
- 设计稿转开发需求
- 多模态资料综合
- 大量文档、图片、页面材料的统一分析

不适合任务：

- 纯 git 审计
- 分支删除终审
- 高风险代码合并裁判
- 极度克制的工程回执
- 单独承担核心逻辑修改终审

使用建议：

只要任务包含截图、PDF、视频、页面体验、设计图或视觉判断，Gemini 3.1 Pro 应优先考虑。纯代码审计和高风险合并判断则不应优先使用它。

---

## 3.6 DeepSeek V4 Pro

定位：代码审计、证据链复核、复杂推理模型。

适合任务：

- PR review 第二意见
- 分支、commit、文件状态核验
- 判断某个文件是否已经进入主线
- 复杂 bug 根因分析
- 架构风险分析
- 检查其他模型的实现是否有逻辑漏洞
- 对删除、清理、合并类操作做证据链复核

不适合任务：

- 多模态 UI 还原
- 截图、视频、视觉类任务
- 无人监督执行不可逆操作
- 非程序员友好型长文案输出

使用建议：

DeepSeek V4 Pro 最适合“查账”。它不一定是第一轮实现模型，但非常适合做复核、审计和事实核验。

---

## 3.7 DeepSeek V4 Flash

定位：快速筛查、小修、小结论辅助模型。

适合任务：

- 日志摘要
- 小 bug 初查
- 简单代码解释
- 快速生成测试思路
- 低风险脚本修改
- 批量文档整理
- 作为 DeepSeek V4 Pro 的前置筛查

不适合任务：

- 复杂 PR 终审
- 多文件架构重构
- 高风险删除、回滚、合并判断
- 核心业务逻辑修改
- 长程无人监督工程任务

使用建议：

DeepSeek V4 Flash 可以快筛，但不能当 V4 Pro 平替。它适合先看一遍，关键结论必须交给更强模型复核。

---

## 3.8 Kimi K2.6

定位：长项目组织、多阶段任务拆解、复杂资料整合模型。

适合任务：

- 长项目拆解
- 多阶段开发计划
- 多模块任务组织
- 文档 + 代码混合分析
- 复杂需求整理成执行路线
- 长文档、长项目资料消化
- 生成项目路线图、执行计划、验收清单

不适合任务：

- 小 bug 快修
- 简单命令排错
- 极短输出任务
- 高风险删除或合并终审
- 需要非常快反馈的轻量任务

使用建议：

Kimi K2.6 适合“大任务”。不要把它浪费在小修小补上。它更适合做长项目组织者和复杂任务拆解者。

## 3.9 GLM-5.1

定位：主力中文工程开发模型。

适合任务：

- 常规功能开发
- 测试驱动修复
- 中小型 PR 实现
- 中文项目文档和交接文档
- 结构化输出
- 前后端普通功能
- 根据明确边界完成工程任务
- 修普通 bug、补测试、补脚本

不适合任务：

- 截图视觉任务
- 1M 级超长上下文任务
- 高风险仓库清理终审
- PR merge 最终裁判
- 无人监督长时间大范围重构

使用建议：

GLM-5.1 不应只当低端工兵。它适合承担主力开发任务，尤其是中文工程场景。但要给明确范围、测试命令和停止条件。

## 3.10 Qwen3.7 Max

定位：强通用执行、复杂任务推进、代码与办公混合模型。

适合任务：

- 复杂功能开发
- 多步骤代码任务
- 文档、表格、代码混合处理
- 中大型项目推进
- 长任务规划
- 需求转实现方案
- 自动化办公与工程结合任务

不适合任务：

- 多模态视觉终审，如果使用的是文本型版本
- 极高风险删除、合并、回滚终审
- 最高难度安全审计
- 与 GPT-5.5 / Opus 4.8 同级别的最终裁判任务

使用建议：

Qwen3.7 Max 适合作为强执行模型。它适合处理复杂开发和办公自动化混合任务，但最终高风险判断仍需更强模型复核。

## 3.11 Qwen3.7 Plus

适合任务：

- 中等复杂前端任务
- 普通代码生成
- 文档处理
- 办公自动化
- 小到中型功能实现
- 图片 + 文本混合理解，如果所用版本支持多模态

不适合任务：

- 超复杂代码审计
- 大型仓库重构
- PR 终审
- 核心业务逻辑改动
- 长时间无人监督开发任务

使用建议：

Qwen3.7 Plus 适合日常中等任务，不要让它承担 Max、Opus、DeepSeek Pro 这类重模型才适合的任务。

## 3.12 MiniMax M3

定位：多模态、长上下文、快速执行型模型。

适合任务：

- 第一轮功能实现
- 产品原型落地
- 前端 UI 修改
- 截图、图片、视频相关分析
- 大上下文代码阅读
- 需求转代码
- 多模态 bug 分析
- 从模糊需求推进到可运行版本

不适合任务：

- 判断文件是否已经进入主线
- 远端分支删除终审
- 工作区清理终审
- 核心业务语义裁判

使用建议：

MiniMax M3 适合先干活、做原型、处理多模态和长上下文任务。由于参数量级未明确披露，且它的优势不等同于最终审计能力，涉及高风险事实核验时应交给更适合审计的模型复核。

## 3.13 MiMo V2.5 Pro

定位：长跑型工程执行模型。

适合任务：

- 长程工程实现
- 批量重构
- 多轮测试与修复
- 大仓库持续修改
- 复杂工程从 0 到 1

不适合任务：

- 最终路线判断
- 高风险删除、清理、回滚终审
- PR merge 裁判
- 没有测试保护的大范围改动
- 只靠聊天做事实核验

使用建议：

MiMo V2.5 Pro 适合承担长时间工程执行，但最终判断、清理、合并和高风险业务逻辑仍应交给更适合审计和终审的模型。

- PR merge 裁判
- 工作区或分支删除判断
- 长程无人监督任务
- 与 Opus、GPT-5.5、DeepSeek V4 Pro 同级别的重审计任务

使用建议：

Hy3 Preview 可以作为推理型副脑或低风险执行模型。它不应硬扛重型开发、复杂审计和最终决策任务。

## 5. 最终使用建议

- 需要“先做出来”：用 MiniMax M3、Qwen3.7 Max、GLM-5.1。
- 需要“稳步开发”：用 Claude Sonnet 4.6、GLM-5.1、Qwen3.7 Plus。
- 需要“处理大任务”：用 Claude Opus 4.8、Claude Opus 4.7、Kimi K2.6、MiMo V2.5 Pro。
- 需要“查账复核”：用 DeepSeek V4 Pro、Claude Opus 4.8、GPT-5.5。
- 需要“多模态产品理解”：用 Gemini 3.1 Pro、MiniMax M3、Qwen3.7 Plus。
- 需要“快筛和低风险辅助”：用 DeepSeek V4 Flash、Hy3 Preview、Qwen3.7 Plus。
- 需要“最终拍板”：用 GPT-5.5、Claude Opus 4.8、DeepSeek V4 Pro。

核心原则：

**模型不是按一个总榜使用，而是按任务分工使用。轻量模型可以辅助，不能硬扛重任务；执行模型可以先干活，但不能单独拍板；审计模型可以复核事实，但不一定最适合原型创造；最终高风险判断必须交给最高可信模型。**
